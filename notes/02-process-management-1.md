## fork — 1回呼ぶと2回返る

普通の関数は1回呼べば1回返る。`fork()` だけは違って、**呼んだ瞬間にプロセス自体が複製され、複製元と複製先の両方が同じ行から実行を再開する**。ソースコードは1つなのに、それを実行しているプロセスが2つある状態になる。

```
                  ret = os.fork()
                        │
            ┌───────────┴───────────┐
            ↓                       ↓
     ┌─────────────┐        ┌─────────────┐
     │ 親プロセス   │        │ 子プロセス   │
     │ ret = 36647 │        │ ret = 0     │
     └──────┬──────┘        └──────┬──────┘
            │                      │
      ret > 0 が真             ret == 0 が真
            ↓                      ↓
     「親プロセス: …」          「子プロセス: …」
```

複製された2つは中身が瓜二つなので、自分が親か子かを区別する手段が要る。それが戻り値の役割で、**これが唯一の違い**になる。子が `0` なのは、自分の pid は `getpid()` でいつでも取れるから。親が子の pid を受け取るのは、後で `wait()` したりシグナルを送るのに必要だから。

```console
$ python3 fork.py
親プロセス: pid=36615, 子プロセスのpid=36647
子プロセス: pid=36647, 親プロセスのpid=36615
```

pid が噛み合っている。同じ親子関係を両側から見た形。

なお**出力順は保証されない**。fork 直後にどちらが先に CPU を得るかはスケジューラ次第で、手元で20回試したときは20回とも親が先だった。

`fork.py` の末尾にある `sys.exit(1)` には到達しない。C言語の `fork()` は失敗時に `-1` を返すため「0でも正でもない＝エラー」の分岐を書くのが定石で、その名残り。Python の `os.fork()` は失敗時に `OSError` を投げる。

### プロセスツリーで親子関係を見る

`fork()` した親子は `pstree -p` にそのまま木構造として現れる。

```console
$ python3 -c 'import os,time; os.fork(); time.sleep(3)' &
親 pid=11
子 pid=17

$ pstree -p
bash(1)-+-pstree(19)---{pstree}(21)
        |-python3(11)-+-python3(17)---{python3}(18)
        |             `-{python3}(16)
        `-{bash}(7)
```

`python3(11)` の下に `python3(17)` がぶら下がっている。これが fork で複製された子で、スクリプトの出力と pid が一致する。**同じプログラムが親子として2つ並ぶ**のが、fork の「複製」という性質をそのまま表している。

波括弧付きの `{python3}(16)` はプロセスではなくスレッド。`pstree` はスレッドも表示するので、プロセスと区別して読む。

## execve — pid はそのまま、中身だけ入れ替わる

`print()` で文字を出すのと `execve("/bin/echo", …)` で出すのでは、画面に出る文字は同じでも**誰が出したかが違う**。前者は自分が出す。後者は**自分を別のプログラムに作り変えて、そいつに出させる**。

Python プロセスを途中で `/bin/sleep` に変身させて、外から `ps` で覗いた結果:

```console
--- execve 前 ---
  PID   COMM      ARGS
69432   python3   python3 exec-demo.py

--- execve 後 ---
  PID   COMM      ARGS
69432   sleep     sleep 5
```

**PID は変わらないのに、動いているプログラムが入れ替わっている。** pid も親子関係も開いているファイルも維持されたまま、中身だけが差し替わる。これが fork（複製）と exec（置換）の役割分担で、シェルが `ls` や `git` を起動するときも、この2段階を踏んでいる。

### システムコール番号は1つだけ

「ファイルを読み出す番号」と「メモリを書き換える番号」が別々に要るのでは、と考えたが違った。

**システムコール番号はカーネルの仕事の名前ではなく、ユーザー空間からカーネルに入る入口の番号**。関所を越えた後の処理はカーネル内部の関数呼び出しにすぎず、番号を持たない。カーネル自身はすでに特権モードで動いていて、自分に申請する必要がないから。

```c
/* /usr/include/x86_64-linux-gnu/asm/unistd_64.h */
#define __NR_execve 59
```

番号が指しているのは `sys_call_table` という配列の添字であって、`do_execve()` のような実装本体ではない。

```
ユーザー空間: レジスタに 59 を入れて syscall 命令
                     ↓
        sys_call_table[59] → __x64_sys_execve    ← 番号が指すのはここ
                     ↓
              do_execve()                        ← 実装本体。番号は持たない
                     ↓
        do_execveat_common() → bprm_execve() → load_elf_binary()
```

### 後戻り不能点は思ったより後ろにある

execve の内部は次の順に進む。

```
1. ファイル名・argv・envp をカーネル空間にコピー   ← 古い空間が消える前に退避
2. ファイルを開く / 先頭を読む / 形式・権限を検証   ← 失敗しても引き返せる
─────────── point of no return ───────────
3. 古いメモリ空間を破棄
4. 新しいメモリ空間を構築、スタックに引数を積む
5. レジスタをセットしてユーザー空間へ復帰
```

この順序には必然性がある。

- 引数の文字列は呼び出し元のメモリにあるので、**破棄より前に退避**しないと消えてしまう
- 失敗時は呼び出し元が生き続けるのが正しい振る舞いなので、**検証は破棄より前**でないとエラーを返せない

だから引き返せる処理を全部先に済ませ、破棄をぎりぎりまで遅らせている。実際に失敗させてみると確かめられる。

```console
開始: pid=57278
  execve(/no/such/file) 失敗 -> errno=2 No such file or directory
  execve(junk.bin)      失敗 -> errno=8 Exec format error
元のプロセスは生きている: pid=57278
  <- ここで初めて置換成功。もう戻れない
```

2回失敗しても同じ pid が生き続けている。検証が破棄より前にある証拠。3回目に成功した直後の行は実行されなかった — **execve は成功すると戻ってこない**。戻る先が消えるので当然だった。

`fork-and-exec.py` の `execve()` 直後にある `exit()` も同じ理由で実行されない。あの行に到達するのは execve が失敗したときだけ。

> **バッファが消える罠**
>
> この実験をパイプ経由で走らせたら、出力が最後の1行しか出なかった。`print()` がユーザー空間のバッファに溜めた文字列が、メモリ空間ごと破棄されたため。
> ファイルディスクリプタはカーネル側にあるので execve をまたいで引き継がれるが、バッファはプロセスのメモリなので消える。C言語で exec の直前に `fflush()` を呼ぶのはこれを防ぐため。`python3 -u` で走らせれば全部出力される。

### strace で流れを確認する

`fork-and-exec.py` を追跡すると、ここまでの話が1本の流れとして見える。

```console
$ strace -f -e trace=clone,execve python3 fork-and-exec.py
execve("/usr/bin/python3", ["python3", "fork-and-exec.py"], …) = 0   # シェルがpythonを起動
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|…|SIGCHLD         # fork の正体
strace: Process 14 attached                                          # 子プロセス誕生
pid=14 からこんにちは                                                 # 子がechoに変身
```

`fork()` がカーネルでは `clone()` として呼ばれている点も見えた。

## プロセスの終了 — ゾンビと終了ステータス

### 実行状態は STAT フィールドで見る

各状態のプロセスを意図的に作って `ps` で観察した。

```console
$ ps -eo pid,stat,comm
  PID STAT COMMAND
    1 Ssl  bash                ← スリープ + セッションリーダー + マルチスレッド
    8 Rl   python3             ← 無限ループ中
   10 Sl   sleep
   12 Sl   python3
   14 T    bash                ← SIGSTOP で停止させた
   21 Z    python3 <defunct>   ← ゾンビ
   23 Rl+  ps                  ← 実行中 + フォアグラウンド
```

STAT は「基本状態 + 修飾子」の組み合わせ。**1文字目が基本状態**。

| 記号 | 状態 | 意味 |
|---|---|---|
| `R` | 実行中/実行可能 | CPU を使っている、または実行キューで順番待ち |
| `S` | 割り込み可能なスリープ | イベント待ち。普段見るプロセスのほとんどはこれ |
| `D` | 割り込み不可能なスリープ | 主にディスク I/O 待ち。中断できないので `kill -9` も効かない |
| `T` | 停止 | `SIGSTOP` などで止められた（Ctrl-Z など） |
| `Z` | ゾンビ | 終了済みだが、親がまだ終了ステータスを回収していない |
| `I` | アイドル | 待機中のカーネルスレッド |

**2文字目以降は修飾子**で、状態ではなく属性を表す。

| 記号 | 意味 |
|---|---|
| `s` | セッションリーダー |
| `l` | マルチスレッド |
| `+` | フォアグラウンドプロセスグループに属する |
| `<` / `N` | 高優先度 / 低優先度 |

`bash` の `Ssl` は「スリープ中の、セッションリーダーで、マルチスレッドなプロセス」と読む。

なお `D` は意図的に作るのが難しく、今回は観察できていない。実務で見るのは NFS がハングしたときなどで、`kill -9` でも消えないプロセスがこれ。

### status は「どう終わったか」を1つの整数に詰め込んでいる

`wait()` が返す終了ステータスには2通りの情報が入る。プロセスの終わり方が「自分で終了した」「殺された」の2通りあるため。

```console
child       status       hex   interpretation
exit(0)          0       0x0   正常終了 / 終了コード=0
exit(42)     10752    0x2a00   正常終了 / 終了コード=42
SIGKILL          9       0x9   シグナルで終了 / シグナル番号=9
SIGSEGV         11       0xb   シグナルで終了 / シグナル番号=11
```

同じ値でもビット位置が違う。

```
exit(42) の場合   0x2a00 = 0010 1010 0000 0000
                           ~~~~~~~~~
                           上位8ビット = 0x2a = 42   ← 終了コード

SIGKILL の場合    0x0009 = 0000 0000 0000 1001
                                     ~~~~~~~~~
                                     下位8ビット = 9  ← シグナル番号
```

**同じ「9」でも、上位に入っていれば `exit(9)`、下位に入っていればシグナル9で殺された**と区別できる。1つの整数で「終了理由」と「その値」の両方を運んでいる。

ビット配置は環境依存なので、生の数値で比較せずマクロで判定する。

| マクロ | 意味 |
|---|---|
| `WIFEXITED(status)` | 自分で終了したか |
| `WEXITSTATUS(status)` | その終了コード（上位8ビット） |
| `WIFSIGNALED(status)` | シグナルで殺されたか |
| `WTERMSIG(status)` | そのシグナル番号（下位8ビット） |

### シェルの `$?` は変換された値

```console
$ bash -c "exit 42"; echo $?
42
$ bash -c "kill -9 \$\$"; echo $?
137
```

`$?` は8ビットしかないので、両方を表現するためシェルが変換している。**シグナルで死んだ場合は `128 + シグナル番号`** で、`137 = 128 + 9`。

`$?` が128を超えていたら、そのプロセスは自分で終了したのではなく殺されたと読める。

### ゾンビが保持しているのはこの status

```
子: exit(42) を実行
      ↓
カーネル: メモリもファイルも解放。status だけ残す   ← この状態がゾンビ
      ↓
親: wait() を呼ぶ
      ↓
カーネル: status を親に渡す → ゾンビ消滅
```

「死んでいるのに消えない」の正体。**親が終了ステータスを受け取るまでカーネルがこの値を保持し続けている**。親が `wait()` を呼ばないプログラムを書くとゾンビが溜まるのは、この受け渡しが行われないから。親が先に死んだ場合は PID 1 が引き取って回収する。

なお `wait()` 自身の戻り値は「終了した子の pid」で、これは status とは別物。複数の子がいるときにどれが終わったかを識別するためにある。

### 孤児プロセスは init が引き取る

親が子より先に死ぬとどうなるか。実際に試すと、**子の親が付け替えられる**。

```console
子 pid=14 / 親 pid=11        ← 最初の親は pid 11
親 pid=11 (この直後に終了する)
子 pid=14 / 親 pid=1         ← 親が死んだ瞬間、親が pid 1 に変わった
```

PPID が 11 から 1 に書き換わっている。これが再親付け（reparenting）。

`init` とは**カーネルが起動時に作る最初のユーザープロセス**のことで、PID は必ず 1 になる。カーネルが直接作るプロセスは init だけで、それ以外のすべてのプロセスは init から始まる `fork()` の連鎖で生まれる。`pstree` で見た木構造の根がこれ。

init は特定のプログラム名ではなく「PID 1 として動くプロセス」という役割の呼び名で、実体は環境によって違う。

| 環境 | PID 1 の実体 |
|---|---|
| 現代の Linux | `systemd`（`/sbin/init` は systemd へのシンボリックリンク） |
| 伝統的な UNIX | `/sbin/init`（SysV init） |
| macOS | `launchd` |
| Docker コンテナ | 起動時に指定したプロセス（この実験では `bash`） |

**なぜ引き取る必要があるのか**は、ゾンビの話とつながっている。孤児をそのまま放置すると、そのプロセスが終了したときに誰も `wait()` を呼ばない。すると status を受け取る相手がいないので、**ゾンビが永久に残り続ける**。

```
親が先に死ぬ
    ↓
子は孤児になる → カーネルが init を新しい親にする
    ↓
子が終了する
    ↓
init が wait() して status を回収 → ゾンビにならずに消える
```

init には「引き取った子が終了したら `wait()` する」という責務がある。これがないとシステムがゾンビで埋まるため、カーネルが強制的に親を付け替えている。

> コンテナの PID 1 が `bash` のような通常のプログラムだと、この回収をしないためゾンビが溜まることがある。`docker run --init` が用意されているのはこのため。

## 実行ファイルは配置の指示書を持っている

カーネルがプログラムをメモリに展開するには、ファイルのどこに何があり、それをメモリのどこに置くかを知る必要がある。その情報が実行ファイル自身に書き込まれている。

ポイントは**ファイルとメモリが別の座標系だ**ということ。ファイルは「先頭から何バイト目」としか言えず、メモリには番地がある。だから両方の情報が要る。

| 領域 | ファイル上オフセット | サイズ | メモリマップ開始アドレス |
|---|---|---|---|
| コード | 0 | 16384 | `0x100000000` |
| データ | 16384 | 16384 | `0x100004000` |

```
  実行ファイル（ディスク）                    メモリ
┌────────────────┐ 0バイト目
│  コード         │ ───16384バイトをコピー──→  0x100000000
├────────────────┤ 16384バイト目
│  データ         │ ───16384バイトをコピー──→  0x100004000
└────────────────┘
```

エントリポイントも番地だが役割が違う。メモリマップ開始アドレスが**領域を置く場所**なのに対し、エントリポイントは**実行を開始する1点**。

実測では先頭から1264バイト後ろだった。コード領域には関数がぎっしり詰まっていて、その先頭が開始位置とは限らないから、情報が別々に要る。

```console
$ readelf -h pause
Class:                ELF64
Type:                 EXEC (Executable file)
Entry point address:  0x401050
```

`Type: EXEC` は `-no-pie` が効いた証拠（macOS では PIE 必須のため無視される → [環境の制約](../README.md#macos-での制約)）。

### PIE かどうかを見分ける

同じソースを `-no-pie` あり／なしでビルドして比べると違いがはっきり出る。

| | `-no-pie` あり | デフォルト（PIE） |
|---|---|---|
| `readelf -h` の Type | `EXEC` (Executable file) | `DYN` (Shared object file) |
| Entry point | `0x401050`（絶対番地） | `0x1060`（先頭からの相対位置） |
| `file` の出力 | `ELF 64-bit LSB executable` | `ELF 64-bit LSB shared object` |

PIE（Position Independent Executable）は「どこに配置されてもいい実行ファイル」なので、共有ライブラリと同じ `DYN` 扱いになり、絶対番地を持たない。配置先は実行時に決まる（ASLR）。

本が `-no-pie` を指定するのは、**毎回同じアドレスが観察できるようにするため**。PIE のままだと実行のたびにメモリ配置が変わり、本文の数値と突き合わせられない。4章で `/proc/<PID>/maps` を見るときに効いてくる。

> `file` の表記はバージョン依存で、Ubuntu 20.04 のものは PIE を `pie executable` ではなく `shared object` と表示する。確実なのは `readelf -h` の `Type`。

## メモリは2階層でできている

「メモリはプロセスごとに用意されるのか、それとも1つのメモリ空間にプロセスが入っていくのか」— どちらも正しくて、見ている階層が違うだけだった。

- **仮想アドレス空間** はプロセスごとに1つずつ作られる
- **物理メモリ** はマシンに1つしかない共有資源

同時に動かした3つの Python プロセスを観察すると、この2層がはっきり出る。

```console
$ ps -o pid,vsz,rss -p ...     # 物理メモリ 8GB のマシン
  PID        VSZ    RSS
61678  33685080   1132
61679  33685084   1608
61680  33685080   1132

VSZ = 仮想アドレス空間 ≈ 32GB / プロセス
RSS = 実際の物理メモリ  ≈ 1.1MB / プロセス
```

1プロセスあたり32GB、3つで96GB。**物理メモリ8GBの12倍**だが矛盾しない。仮想アドレス空間は地図にすぎず、実際に物理メモリを消費しているのは RSS の1.1MBだけ。残りは線を引いただけで物件を建てていない土地にあたる。

対応付けはプロセスごとの**ページテーブル**が管理し、CPU の MMU が変換する。これはプロセス保護の正体でもあって、他プロセスのページは自分の地図に載っていないので、どんな番地を指定しても到達できない。禁止されているのではなく、道が存在しない。

### 同じ変数、違うアドレス、同じページ内オフセット

3つのプロセスで同じ変数のアドレスを出力した結果:

```
pid=61680  0x109bb0d90
pid=61679  0x10d504d90
pid=61678  0x10bfa8d90
```

バラバラなのは ASLR がアドレスをランダム化しているから。仮想アドレスなので自由にずらせる。

ただし**下位が全部 `d90` で一致**している。このマシンのページサイズは16KBで、ASLR はページ単位でずらすため、ページ内のオフセットは変わらない。地図の描き直しがページ単位で行われている証拠。

この続き（コピーオンライト、デマンドページング）は4章・5章で扱われる。
