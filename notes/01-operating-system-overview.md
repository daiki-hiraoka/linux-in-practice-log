# 1章 システムの初期化

電源を入れてから Linux が使えるようになるまでに、性格の違うプログラムが順番にバトンを渡していく。その境界がどこにあるかを整理した記録。

---

## 起動の流れ

```
電源ON
  ↓
① ファームウェア  … マザーボードに焼き込まれたプログラム（BIOS / UEFI）
  ↓
② ブートローダ    … ディスクに入っているプログラム（GRUB など）
  ↓
③ カーネル
  ↓
④ init (PID 1)   … 最初のユーザープロセス
```

## ファームウェアとブートローダの違い

**ファームウェアはハードウェア側のプログラム**。マザーボードの ROM に焼き込まれていて、電源を入れると最初に動く。OS より前に存在するので、Linux が入っていようが Windows が入っていようが同じものが動く。

**ブートローダは OS 側のプログラム**。ディスクにインストールされていて、カーネルを探してメモリに展開し、制御を渡す。

| | ファームウェア | ブートローダ |
|---|---|---|
| どこにある | マザーボードの ROM | ディスク |
| 所属 | ハードウェア | OS |
| OS を知っているか | 知らない | 知っている |
| 主な仕事 | ハードウェア初期化、起動デバイス探し | カーネルを探してメモリに展開 |

### なぜ2段階に分かれているのか

**ファームウェアが OS を知らないから**。

ファームウェアはハードウェアの付属品なので、そのディスクに入っている OS が何なのか、カーネルのファイルがどこにあるのかを知らない。そもそも ext4 のようなファイルシステムを読む機能すら持っていない（従来の BIOS の場合）。

BIOS にできるのは「起動ディスクの先頭512バイトを読んで実行する」程度で、512バイトでは Linux カーネルを読み込む処理など書けない。そこで **OS のことを知っているプログラム＝ブートローダ**が必要になる。

マザーボードを交換するとファームウェアが変わり、OS を入れ替えるとブートローダが変わる。この境界が役割分担そのもの。

---

## 起動デバイスとは

**ブートローダが入っているストレージ**のこと。ファームウェアには起動順序（boot order）が設定されていて、上から順に「このデバイスから起動できるか」を確認していく。

```
ファームウェア: 「どれから起動できる？」
    ↓
  ① USB メモリ     → 挿さっていない → 次へ
  ② 内蔵SSD        → ブートローダ発見 → こいつに制御を渡す ✓
  ③ ネットワーク
```

| デバイス | 使う場面 |
|---|---|
| 内蔵 SSD / HDD | 普段の起動 |
| USB メモリ | OS のインストール、レスキュー |
| DVD / ISO イメージ | 同上（VM ではこれが多い） |
| ネットワーク（PXE） | サーバーの大量展開 |

### 「起動できる」の判定方法

ファームウェアは中身を理解しているわけではなく、**決まった場所に決まった目印があるか**だけを見ている。

- **BIOS** … デバイスの先頭512バイトを読み、末尾2バイトが `0x55AA` かを確認する。あれば起動可能とみなしてその512バイトを実行する
- **UEFI** … EFI システムパーティション（FAT形式）に `.efi` の実行ファイルがあるかを確認する

ファイルシステムの中身まで解釈しないのは、やはり「ファームウェアは OS を知らない」ため。

OS インストール時に BIOS 設定で USB を内蔵SSDより上に持ってくる操作は、**探す順番を変えて USB のブートローダを先に見つけさせている**ということ。

---

## デバイスはどう認識されるのか

「マザーボードのこの場所に繋がっているからメモリ／SSD」という認識は**半分正しい**。

### 場所で決まるもの、決まらないもの

メモリスロットにはメモリしか刺さらないし、CPU ソケットには CPU しか載らない。物理的な形状と配線が専用なので、ここは場所で決まる。

一方で USB や PCIe のような**汎用バス**は、同じ形の口にまったく違う種類のデバイスが繋がる。

```
USB ポート   → キーボード？ マウス？ USBメモリ？ カメラ？ 外付けSSD？
PCIe スロット → グラボ？ NVMe SSD？ ネットワークカード？
```

さらに専用スロットであっても、刺さっているメモリが 8GB なのか 32GB なのかは場所からは分からない。

### だから問い合わせる

ファームウェアは各デバイスに話しかけて自己申告させる。デバイス側には自分の素性を答える仕組みが組み込まれている。

| デバイス | 問い合わせの仕組み | 得られる情報 |
|---|---|---|
| メモリ | モジュール上の SPD チップを読む | 容量、速度、タイミング |
| SATA / NVMe | `IDENTIFY DEVICE` コマンドを送る | 型番、容量、対応機能 |
| USB | デバイスディスクリプタを要求 | ベンダーID、製品ID、種類 |
| PCIe | コンフィグレーション空間を読む | ベンダーID、デバイスID |

```
Product ID: 0x8514
Vendor ID:  0x05ac  (Apple Inc.)
Speed:      Up to 480 Mb/s
```

この `0x05ac` は USB の規格団体が管理している Apple の登録番号で、**ケーブルの繋ぎ方から分かるものではなく、デバイスに聞いて返ってきた答え**。

まとめると2段階になっている。

```
① 物理的な位置 → 「ここに何かが繋がっている」「この種類のバスだ」
② 問い合わせ   → 「お前は誰だ？」→ ベンダーID・型番・容量を回収
```

電源投入後に画面が真っ暗な数秒間、裏でこの問い合わせが全デバイスに対して走っている。場所で決め打ちしていないからこそ、USB メモリを挿し替えても、SSD を大容量のものに交換しても、設定を書き換えずに認識される。

### デバイス側にあるのは「データ」であって実行ファイルではない

問い合わせに対してデバイスが返すのは、決まった場所に決まった形式で置かれた**データ**。デバイスは読まれるのを待っているだけで、何も実行していない。名札が貼ってあって、ファームウェアがそれを読んでいるイメージ。

ただし例外として、**ホストの CPU に実行させるプログラムを積んでいるデバイス**もある。Option ROM（オプションROM）と呼ばれる。

| 例 | 何をするか |
|---|---|
| グラフィックカードの VGA BIOS | OS 起動前に画面表示を可能にする |
| ネットワークカードの PXE コード | ネットワーク経由での起動を可能にする |
| RAID カードの BIOS | 起動時に RAID 構成画面を出す |

起動時に「Press Ctrl+I to enter RAID configuration」のような画面が出るのは、マザーボードのファームウェアではなく**カード側のプログラムが実行されている**。UEFI では同じ役割を `.efi` 形式の UEFI ドライバが担う。

混同しやすいものを整理すると4種類ある。

| 何 | どこにある | 誰が実行するか |
|---|---|---|
| 素性データ（ID、容量） | デバイス上のROM | **実行しない。読むだけ** |
| デバイス自身のファームウェア | デバイス上 | デバイス内蔵のコントローラ |
| Option ROM / UEFIドライバ | デバイス上のROM | **ホストのCPU**（起動時） |
| デバイスドライバ | OS側（ディスク上） | ホストのCPU（OS起動後） |

SSD にもコントローラ用のプログラムが入っているが、それは SSD 自身が動くためのもので、PC の CPU が実行するわけではない。「SSD のファームウェアアップデート」はこれを書き換えている。

## Docker コンテナには起動シーケンスがない

コンテナの `/boot` を見ると空だった。

```console
$ ls -A /boot
（何もない）
```

**コンテナはカーネルを持たない。** ホストのカーネルを共有して動いている。

つまりコンテナには ①ファームウェア も ②ブートローダ も ③カーネル起動 も存在せず、**いきなり ④ の PID 1 から始まる**。`docker compose run` した瞬間に PID 1 が生まれているのはこのため。コンテナの起動が一瞬なのは、①〜③を丸ごと省略しているから。

この章の起動シーケンスを実際に観察したければ、コンテナではなく VM が必要になる。
