# fork と execve の実測ノート

『[試して理解]Linuxのしくみ 増補改訂版』（武内覚）第2章の実験を、実際に走らせて数値で確かめた記録。
macOS でつまずいた点と、Docker で実験環境を組み直すまでを残している。

- 教材サンプルコード: [satoru-takeuchi/linux-in-practice-2nd](https://github.com/satoru-takeuchi/linux-in-practice-2nd)
- 母艦: macOS / Apple Silicon
- 実験環境: Docker (amd64 + arm64)

---

## fork — 1回呼ぶと2回返る

普通の関数は1回呼べば1回返る。`fork()` だけは違って、**呼んだ瞬間にプロセス自体が複製され、複製元と複製先の両方が同じ行から実行を再開する**。ソースコードは1つなのに、それを実行しているプロセスが2つある状態になる。

```
                  ret = os.fork()
                        │
            ┌───────────┴───────────┐
            ↓                       ↓
     ┌─────────────┐        ┌─────────────┐
     │ 親プロセス   │        │ 子プロセス   │
     │ ret = 36647 │        │ ret = 0     │
     └──────┬──────┘        └──────┬──────┘
            │                      │
      ret > 0 が真             ret == 0 が真
            ↓                      ↓
     「親プロセス: …」          「子プロセス: …」
```

複製された2つは中身が瓜二つなので、自分が親か子かを区別する手段が要る。それが戻り値の役割で、**これが唯一の違い**になる。子が `0` なのは、自分の pid は `getpid()` でいつでも取れるから。親が子の pid を受け取るのは、後で `wait()` したりシグナルを送るのに必要だから。

```console
$ python3 fork.py
親プロセス: pid=36615, 子プロセスのpid=36647
子プロセス: pid=36647, 親プロセスのpid=36615
```

pid が噛み合っている。同じ親子関係を両側から見た形。

なお**出力順は保証されない**。fork 直後にどちらが先に CPU を得るかはスケジューラ次第で、手元で20回試したときは20回とも親が先だった。

## execve — pid はそのまま、中身だけ入れ替わる

`print()` で文字を出すのと `execve("/bin/echo", …)` で出すのでは、画面に出る文字は同じでも**誰が出したかが違う**。前者は自分が出す。後者は**自分を別のプログラムに作り変えて、そいつに出させる**。

Python プロセスを途中で `/bin/sleep` に変身させて、外から `ps` で覗いた結果:

```console
--- execve 前 ---
  PID   COMM      ARGS
69432   python3   python3 exec-demo.py

--- execve 後 ---
  PID   COMM      ARGS
69432   sleep     sleep 5
```

**PID は変わらないのに、動いているプログラムが入れ替わっている。** pid も親子関係も開いているファイルも維持されたまま、中身だけが差し替わる。これが fork（複製）と exec（置換）の役割分担で、シェルが `ls` や `git` を起動するときも、この2段階を踏んでいる。

### システムコール番号は1つだけ

「ファイルを読み出す番号」と「メモリを書き換える番号」が別々に要るのでは、と考えたが違った。

**システムコール番号はカーネルの仕事の名前ではなく、ユーザー空間からカーネルに入る入口の番号**。関所を越えた後の処理はカーネル内部の関数呼び出しにすぎず、番号を持たない。カーネル自身はすでに特権モードで動いていて、自分に申請する必要がないから。

```c
/* /usr/include/x86_64-linux-gnu/asm/unistd_64.h */
#define __NR_execve 59
```

番号が指しているのは `sys_call_table` という配列の添字であって、`do_execve()` のような実装本体ではない。59番の箱に入っている入口関数から、番号を持たないカーネル関数が順に呼ばれていく。

### 後戻り不能点は思ったより後ろにある

execve の内部は次の順に進む。

```
1. ファイル名・argv・envp をカーネル空間にコピー   ← 古い空間が消える前に退避
2. ファイルを開く / 先頭を読む / 形式・権限を検証   ← 失敗しても引き返せる
─────────── point of no return ───────────
3. 古いメモリ空間を破棄
4. 新しいメモリ空間を構築、スタックに引数を積む
5. レジスタをセットしてユーザー空間へ復帰
```

この順序には必然性がある。先にメモリを捨ててしまうと、**エラーを返そうにも戻り先のプログラムが消えている**。だから引き返せる処理を全部先に済ませ、破棄をぎりぎりまで遅らせている。

実際に失敗させてみると、確かめられる。

```console
開始: pid=57278
  execve(/no/such/file) 失敗 -> errno=2 No such file or directory
  execve(junk.bin)      失敗 -> errno=8 Exec format error
元のプロセスは生きている: pid=57278
  <- ここで初めて置換成功。もう戻れない
```

2回失敗しても同じ pid が生き続けている。検証が破棄より前にある証拠。3回目に成功した直後の行は実行されなかった — **execve は成功すると戻ってこない**。戻る先が消えるので当然だった。

> **バッファが消える罠**
> 最初この実験をパイプ経由で走らせたら、出力が最後の1行しか出なかった。`print()` がユーザー空間のバッファに溜めた文字列が、メモリ空間ごと破棄されたため。ファイルディスクリプタはカーネル側にあるので引き継がれるが、バッファはプロセスのメモリなので消える。C言語で exec の直前に `fflush()` を呼ぶのはこれを防ぐため。

## 実行ファイルは配置の指示書を持っている

カーネルがプログラムをメモリに展開するには、ファイルのどこに何があり、それをメモリのどこに置くかを知る必要がある。その情報が実行ファイル自身に書き込まれている。

ポイントは**ファイルとメモリが別の座標系だ**ということ。ファイルは「先頭から何バイト目」としか言えず、メモリには番地がある。だから両方の情報が要る。

| 領域 | ファイル上オフセット | サイズ | メモリマップ開始アドレス |
|---|---|---|---|
| コード (`__TEXT`) | 0 | 16384 | `0x100000000` |
| データ (`__DATA_CONST`) | 16384 | 16384 | `0x100004000` |

```
  実行ファイル（ディスク）                    メモリ
┌────────────────┐ 0バイト目
│  コード         │ ───16384バイトをコピー──→  0x100000000
├────────────────┤ 16384バイト目
│  データ         │ ───16384バイトをコピー──→  0x100004000
└────────────────┘
```

エントリポイントも番地だが役割が違う。メモリマップ開始アドレスが**領域を置く場所**なのに対し、エントリポイントは**実行を開始する1点**。

実測では `entryoff 1264`、つまりコードの先頭ではなく1264バイト後ろだった。コード領域には関数がぎっしり詰まっていて、その先頭が開始位置とは限らないから、情報が別々に要る。

```console
$ readelf -h pause
Class:                ELF64
Type:                 EXEC (Executable file)
Entry point address:  0x401050
```

`Type: EXEC` は `-no-pie` が効いた証拠。macOS (Apple Silicon) は PIE が必須なのでこのオプションは無視され、アドレスも固定にならない。

## メモリは2階層でできている

「メモリはプロセスごとに用意されるのか、それとも1つのメモリ空間にプロセスが入っていくのか」— どちらも正しくて、見ている階層が違うだけだった。

- **仮想アドレス空間** はプロセスごとに1つずつ作られる
- **物理メモリ** はマシンに1つしかない共有資源

同時に動かした3つの Python プロセスを観察すると、この2層がはっきり出る。

```console
$ ps -o pid,vsz,rss -p ...     # 物理メモリ 8GB のマシン
  PID        VSZ    RSS
61678  33685080   1132
61679  33685084   1608
61680  33685080   1132

VSZ = 仮想アドレス空間 ≈ 32GB / プロセス
RSS = 実際の物理メモリ  ≈ 1.1MB / プロセス
```

1プロセスあたり32GB、3つで96GB。**物理メモリ8GBの12倍**だが矛盾しない。仮想アドレス空間は地図にすぎず、実際に物理メモリを消費しているのは RSS の1.1MBだけ。残りは線を引いただけで物件を建てていない土地にあたる。

対応付けはプロセスごとの**ページテーブル**が管理し、CPU の MMU が変換する。これはプロセス保護の正体でもあって、他プロセスのページは自分の地図に載っていないので、どんな番地を指定しても到達できない。禁止されているのではなく、道が存在しない。

### 同じ変数、違うアドレス、同じページ内オフセット

3つのプロセスで同じ変数のアドレスを出力した結果:

```
pid=61680  0x109bb0d90
pid=61679  0x10d504d90
pid=61678  0x10bfa8d90
```

バラバラなのは ASLR がアドレスをランダム化しているから。仮想アドレスなので自由にずらせる。

ただし**下位が全部 `d90` で一致**している。このマシンのページサイズは16KBで、ASLR はページ単位でずらすため、ページ内のオフセットは変わらない。地図の描き直しがページ単位で行われている証拠。

## 実験環境（Docker）

2章の途中まで Mac で進めたが、`/proc` も `strace` も存在せず、`readelf` は入っておらず、そもそもバイナリが ELF ではなく Mach-O だった。Docker で Ubuntu 20.04 の環境を用意して切り替えた。

このリポジトリの `Dockerfile` と `compose.yaml` を**教材リポジトリのルートに置いて**使う。

```bash
git clone https://github.com/satoru-takeuchi/linux-in-practice-2nd.git
cd linux-in-practice-2nd
cp /path/to/this-repo/{Dockerfile,compose.yaml} .

docker compose run --rm x86    # 通常はこちら
docker compose run --rm arm    # strace を使うときだけこちら
```

### アーキテクチャを2つ用意した理由

本は x86_64 前提で書かれているので、Apple Silicon 上でも `platform: linux/amd64` で動かせばシステムコール番号などが本文と一致する。ところが**エミュレーション環境では `strace` が動かない**。

```
strace: test_ptrace_get_syscall_info: PTRACE_TRACEME: Function not implemented
```

QEMU が `ptrace` を実装していないためで、権限や seccomp の問題ではない。そこで両方をサービスとして定義し、使い分けることにした。

| | amd64（エミュレーション） | arm64（ネイティブ） |
|---|---|---|
| 本文との一致 | 一致（execve=59, `-no-pie` が効く） | 不一致（execve=221） |
| `strace` | 動かない | 動く |
| 速度 | 遅い | 速い |

実際に `fork-and-exec.py` を追跡すると、ここまでの話が1本の流れとして見える。

```console
$ strace -f -e trace=clone,execve python3 fork-and-exec.py
execve("/usr/bin/python3", ["python3", "fork-and-exec.py"], …) = 0   # シェルがpythonを起動
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|…|SIGCHLD         # fork の正体
strace: Process 14 attached                                          # 子プロセス誕生
pid=14 からこんにちは                                                 # 子がechoに変身
```

`fork()` がカーネルでは `clone()` として呼ばれている点も見えた。

なお仮想化関連パッケージ（qemu-kvm, libvirt）は、コンテナから KVM を触れないため入れていない。10章に入るときは VM を立てる必要がある。

## つまずきメモ

本題以外で詰まったところ。

| 症状 | 原因と対処 |
|---|---|
| `cc: error: unknown option '-o'` | `cc` が Claude Code の起動エイリアスになっていた。コンパイラに届いていない。`\cc` か `clang` で回避 |
| `zsh: command not found: readelf` | macOS に readelf はない。そもそも対象が ELF ではなく Mach-O なので入れても読めない。`otool -h` / `otool -l` が対応するツール |
| `warning: argument unused: '-no-pie'` | Apple Silicon は PIE 必須のため無視される。アドレスを固定して観察したいなら Linux 環境が要る |
| `strace: PTRACE_TRACEME: Function not implemented` | QEMU エミュレーション下では ptrace が使えない。arm64 ネイティブのコンテナに切り替える |
| パイプに繋ぐと出力が消える | バッファに溜まった内容が execve でメモリごと破棄される。`python3 -u` か exec 前のフラッシュで回避 |
